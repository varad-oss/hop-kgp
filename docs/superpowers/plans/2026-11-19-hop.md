# Hop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Hop, a mobile-first web app where KGP students post a trip and land in a destination×day lobby. In the lobby they propose a plan, vote "I'm in", and lock it into a private pod with phone numbers and an equal fare split. Everything is built on the Nexconn Chat SDK, live by Fri 20 Nov evening and submitted by Sun 22 Nov 21:00 IST.

**Architecture:** A Next.js (App Router, TypeScript) app in `web/`, deployed to Vercel.
- **Server:** route handlers hold every secret. They talk to Postgres (Supabase) through a thin `Db` interface and to the Nexconn Platform API through a signed `NexconnApi` client.
- **State:** the trip state machine (join, leave, lock) lives in Postgres functions, so seat caps and one-vote-per-lobby are atomic. Nexconn group channels and custom messages are the live mirror the client renders.
- **Auth:** Supabase handles Google sign-in (restricted to `@kgpian.iitkgp.ac.in`) and anonymous sessions (for the demo).

**Tech stack:**
- Next.js, React and Tailwind; Vitest.
- `@electric-sql/pglite` (in-process Postgres for tests) and `pg` (production).
- `@supabase/ssr` and `@supabase/supabase-js` (auth only).
- `@nexconn/engine` and `@nexconn/chat` 26.2.1.
- `@google/genai` (P1).
- Playwright MCP for browser checks.

**Spec:** `docs/superpowers/specs/2026-11-19-hop-design.md`. Read it with this plan. Rules and rubric are in `docs/HACKATHON_BRIEF.md`.

## Global Constraints

**Repo, runtime and hosting**
- The app lives in `web/`. Vercel root directory is `web`, functions region is `bom1`, and Node is ≥ 22 with pnpm.

**Nexconn**
- `@nexconn/engine` and `@nexconn/chat` are pinned at exactly `26.2.1` (no `^`). No ChatUI, no Call SDK, no typing indicators, no push code.
- The client initializes with `areaCode: AreaCode.SG`.
- The server uses `https://api.sg-light-api.com`, failing over to `https://api-b.sg-light-api.com` after a 5 s timeout.
- Nexconn IDs may contain only letters and digits (≤ 64):
  - users: `u` + uuid-hex for real users, `demo` + uuid-hex for demo users
  - lobbies: `l` + hex
  - pods: `p` + hex
  - bot: `hopbot`
- The spec's "`demo_` prefix" means the DB flag `is_demo`, the Nexconn prefix `demo`, and "Demo · " in display names.
- Custom message types are exactly `Hop:Intent`, `Hop:Proposal` and `Hop:Ticket`. Register each with `isPersisted: true, isCounted: true` before `connect`.
- Server sends of these cards use `isEchoToSender: 1`, and `Hop:Proposal` also uses `hasMetadata: true`.
- Proposal metadata values are strings. The only keys are `status`, `inCount`, `bags`, `voters` (comma-separated Nexconn IDs) and `podId`.

**Secrets**
- Server env only: `NEXCONN_APP_SECRET`, `DATABASE_URL`, `GEMINI_API_KEY`.
- The client sees only `NEXT_PUBLIC_*` (the App Key, Supabase URL and anon key, site URL).
- A gitleaks pre-commit hook runs on every commit. `research_notes/`, `reports/`, `.claude/`, `NEXCONN_CLAUDE_CODE_PROMPT.md` and `web/.env*` (except `.env.example`) are git-ignored (my call: third-party research stays out of the public repo).

**Data**
- All tables live in schema `hop` with `ENABLE ROW LEVEL SECURITY` and no policies. Only the server touches them, via `DATABASE_URL`. Never create tables in `public`: Supabase exposes `public` to the anon key.
- **Demo isolation:** every read path filters by `is_demo` and demo ownership, stats exclude demo rows, and demo travellers never get a Nexconn token.
- **No money:** fare splits are display only.

**Copy and UI**
- Locale `en-IN`: ₹ with en-IN grouping (₹2,800), times in `Asia/Kolkata`, dates like `Thu 26 Nov`.
- Mobile-first at 360–430 px: tap targets ≥ 44 px, WCAG AA contrast. No service worker.
- `@nexconn/*` is dynamically imported only after sign-in. The landing page is static.
- Trip dates run from today (IST) to `2027-01-31`.

**Commits** end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Phone numbers in lobby chat.** Numbers typed as `+91 98765 43210`, `98765-43210`, `098765 43210` or spaced digits must be blocked, but times, fares and dates (`6:30`, `₹2,800`, `26-11-2026`) must not be. Tests: Task 4 (`containsPhone`) and Task 17 (webhook).
2. **Lock retried.** Lock tapped twice, or retried after a dropped response, returns the same pod, and exactly one Trip Ticket is posted. Tests: Task 8 (`already_locked`) and Task 11 (materialize twice).
3. **Last seat.** When the last seat is taken, the next "I'm in" gets `full`. The card shows Full and a pod never exceeds `seats`. Test: Task 8. The real race is guarded by `FOR UPDATE`; also check it manually with two phones in Task 19.
4. **Nexconn fails mid pod setup.** The pod shows "Setting up your pod…" and completes when reopened; the ticket is sent once. Test: Task 11.
5. **Personal Gmail sign-in.** It lands on the landing page with the "Not a KGP student? Try the demo" banner, not an error. Test: Task 5. Also tested: joining after departure returns `departed` (Task 8).

### Task 8: Trip state machine in Postgres

**Files:**
- Create: `web/db/migrations/0002_state_machine.sql`
- Test: `web/tests/db/stateMachine.test.ts`

**Interfaces:**
- Produces three SQL functions in schema `hop`. Each locks the proposal row with `SELECT … FOR UPDATE` first.
  - `hop.join_proposal(p_proposal uuid, p_user uuid, p_now timestamptz) returns table(result text, in_count int, pod_id uuid, moved_from uuid)`
    - `result` is one of `joined`, `already`, `full`, `departed`, `closed`, `busy` or `not_in_lobby`.
    - Rules:
      - The user needs an intent in the proposal's lobby.
      - An open proposal is capped at `seats` votes.
      - Joining an open proposal removes the user's vote on any other open proposal in that lobby and returns it as `moved_from`.
      - A user who is `in` a pod in the same lobby gets `busy`.
      - On a locked proposal with free seats before `depart_at`, the user is inserted into `pod_members` as `in`.
      - A cancelled proposal gives `closed`, and `p_now >= depart_at` gives `departed`.
  - `hop.leave_proposal(p_proposal uuid, p_user uuid, p_now timestamptz) returns table(result text, in_count int, pod_id uuid)`
    - `result` is `left` or `not_in`.
    - On an open proposal it deletes the vote. On a locked one it sets the member to `left`.
    - If the pod reaches 0 `in` members, the pod is set to `archived` and the proposal to `cancelled`.
  - `hop.lock_proposal(p_proposal uuid, p_user uuid) returns table(result text, pod_id uuid)`
    - `result` is one of `locked`, `already_locked`, `not_voter`, `too_few` or `closed`.
    - It requires at least 2 votes and the caller among them.
    - It creates the pod (`status 'pending'`, `channel_id` = `'p' || replace(pod_id::text,'-','')`) with every voter as `in`, and deletes those voters' votes on other open proposals in the lobby.
    - When the caller is already a member of the existing pod, it returns `already_locked` with the same `pod_id`.
